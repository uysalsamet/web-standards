# ADR-0011 — Internationalisation: i18next + react-i18next with typed keys and a parity gate

- **Status:** Accepted
- **Date:** 2026-09-07
- **Related rules:** [GEN-14], [I18N-01]..[I18N-42], [VER-05], [CI-12], [TOOL-01], [SEO-08]

## Context

Every product in scope ships at least Turkish, most ship Turkish and English, and the
customer is a public institution: a half-translated screen is not a cosmetic defect, it is
a complaint to the municipality. Three failure modes have to be designed out, not reviewed
out:

1. **Literal strings.** A developer (or an agent) writes `<button>Kaydet</button>` and the
   second locale never sees it. Caught by lint ([I18N-03]).
2. **Key drift.** `en` gains five keys that `tr` does not have, or a placeholder is renamed
   in one locale only. Nothing throws; the user gets English text or a literal `{{adet}}`.
   Caught by the parity gate ([I18N-02]).
3. **Typos in keys.** `t('parking.list.titel')` renders the key to the user. Caught by the
   compiler ([I18N-17]).

Secondary requirements: Turkish-specific casing and collation (`I`/`ı`, `i`/`İ`,
`Intl.Collator('tr')`), plural handling that survives a language with a single noun form,
rich text with links inside sentences without an HTML sink, and a locale strategy that does
not conflict with the URL-based locale that SEO products need ([SEO-08]).

The constraint from [GEN-01] and [VER-05]: no framework change, no second runtime, and the
bundle cost has to fit the budget in [PERF-02]. Whatever is chosen must also be
mechanically checkable by a dependency-free Node script, because the parity gate has to run
in CI on every PR ([GEN-23]).

## Options

### A) i18next + react-i18next, single bundled namespace, generated `keys.d.ts`, `check-i18n.mjs` (CHOSEN)

**Strengths:**
- The three defences compose cleanly: `eslint-plugin-i18next` for literals,
  `CustomTypeOptions` for key typos at compile time, and a 300-line dependency-free script
  for cross-locale parity. No other option has all three off the shelf.
- Plain JSON resource files. That is what makes the parity checker possible without a
  compiler or an AST: a translator, a reviewer, `git diff` and the script all read the same
  format.
- CLDR plurals (`_one`/`_other`) and context suffixes (`_driver`) are part of the key name,
  so they are visible to the parity checker as ordinary keys. Compiled formats hide this
  inside a message AST.
- `<Trans>` renders React elements for rich text, so a translation never has to touch
  `innerHTML` ([I18N-20], [SEC-01]).
- Runtime language switching without a reload, which the Tier 0 apps ([SEO-02]) need for a
  language toggle in the header.
- Already in production in the reference deployment; the migration is a file reorganisation
  ([I18N-05]), not a rewrite of every call site.
- Bundle cost measured: i18next + react-i18next is about 17 KB gzipped, plus roughly
  15 to 40 KB per locale bundle. Inside the budget for the two or three locales in [I18N-15].

**Weaknesses:**
- The runtime is the largest of the four options. A compile-time library would ship less.
- Type safety is bolted on: `CustomTypeOptions` needs a generated file that can drift, which
  is why [I18N-17] requires a CI diff check ([CI-12]).
- Nothing in the library enforces parity. That is exactly why the standard carries its own
  checker; the library would happily fall back to English forever ([I18N-14]).
- The plugin/backend ecosystem invites configuration sprawl (detectors, backends, post
  processors). [I18N-13] fixes one config to prevent it.
- No ICU MessageFormat by default (select, nested plural, gender) without the ICU plugin.
  Acceptable: [I18N-19] and [I18N-23] cover the cases the products actually have.

### B) react-intl / FormatJS (ICU MessageFormat)

**Strengths:** ICU is the industry message syntax and handles select/plural/ordinal in one
string; excellent `Intl` integration; a mature extraction toolchain (`formatjs extract`)
that finds messages in source and produces the catalogue, which removes a class of "key not
in file" errors.

**Weaknesses:** The default workflow uses the English source string as the message id, which
is precisely the anti-pattern [I18N-07] forbids: an English copy edit orphans every other
locale. Explicit ids are possible but fight the tooling. Compiled ICU ASTs are harder to
diff and cannot be checked for placeholder parity by a simple script. `<FormattedMessage>`
with rich text requires passing chunk functions, which is more ceremony than `<Trans>`.
Turkish gains nothing from ICU's plural machinery because the language has one noun form.

### C) Lingui

**Strengths:** Compile-time macros produce small runtime code; ICU under the hood; message
extraction with a good CLI; `<Trans>Text</Trans>` with the source text inline is genuinely
pleasant to write.

**Weaknesses:** The inline-source-text model is the same id-is-the-English-sentence problem
as B. The macro step is a Babel/SWC plugin in the Vite pipeline, one more thing that has to
survive every Vite and React Compiler upgrade ([VER-08]) in a stack that already runs
`babel-plugin-react-compiler`. Catalogues are `.po` or compiled JS, so `check-i18n.mjs`
would need a format-specific parser. Smaller ecosystem; when it breaks against a new React
major, the fix is not already written by someone else.

### D) Paraglide (inlang)

**Strengths:** Compiles each message to a tree-shakeable function, so unused messages are
not shipped at all: the smallest runtime of the four, and a missing key is a build error by
construction, which solves defect (3) more elegantly than a generated `.d.ts`.

**Weaknesses:** Parity is enforced per message *function*, not per locale file, and the
generated output is not something a translator or a reviewer reads. The tooling assumes its
own editor and project file; adopting it means adopting a workflow, not a library. Runtime
language switching is deliberately awkward because the design targets per-locale builds,
which conflicts with the Tier 0 language toggle. Youngest project of the four and the least
represented in the training data every coding agent in this organisation uses, which matters
when the standard's primary consumer is an agent.

## Decision

**i18next + react-i18next**, with the standard supplying what the library does not:
a lint rule for literals, a generated `keys.d.ts` for key typos, and `tools/check-i18n.mjs`
for cross-locale parity, plural parity and placeholder parity.

The deciding argument is not the library's feature list, it is the failure mode that
actually happens. Key drift between `tr` and `en` is the defect that reaches users, and it
is only detectable if the catalogue is a plain, per-locale, per-namespace JSON file that a
90-line script can flatten and compare. Options B, C and D all move the catalogue closer to
the compiler and further from a text file, and all three make the English sentence the
default key. i18next keeps the source of truth in a format the gate can read, and the gate
is what makes [GEN-14] real rather than aspirational.

## Accepted costs

- The largest runtime of the four options (about 17 KB gzipped) plus every bundled locale,
  on every page load including the ones with no visible text. Bounded by [I18N-15] at three
  locales; beyond that the standard has an unresolved lazy-loading question.
- Type safety depends on a generated, committed file. It can drift; the CI diff check
  ([CI-12]) is an extra pipeline step whose failure message ("run `npm run gen:i18n-keys`")
  every developer will see at least once.
- The organisation maintains `check-i18n.mjs` itself. When the namespace model changes (real
  i18next namespaces for lazy loading), the script's prefix logic changes with it.
- No ICU. A future locale with three or more plural forms (Arabic, Russian, Polish) needs the
  ICU plugin or a per-form key set, and the parity checker's plural rules were written for
  the `one`/`other` case.
- Translations are hand-edited JSON in PRs ([I18N-42]). This does not scale to non-developer
  translators, and adopting a TMS later means finding one that round-trips the exact key set.
- The single `translation` namespace holding feature prefixes is a deliberate simplification.
  It makes cross-namespace keys ergonomic and the checker simple, at the price of an
  extra refactor when per-namespace lazy loading is introduced.

## What would change this decision

- A fourth locale, or a locale with more than two plural forms. That forces either the ICU
  plugin or a re-evaluation, and it is the point at which B becomes competitive.
- A non-developer translation workflow becoming a requirement. If the chosen TMS has
  first-class support for one of the other formats and round-trips key sets exactly, the
  catalogue format is back on the table.
- Paraglide (or an equivalent compile-time library) shipping a locale-file format that a
  simple script can check for parity, plus a documented runtime language switch. That would
  remove the bundle cost without giving up the gate.
- i18next dropping React 19 support, or react-i18next lagging a React major by more than one
  minor release ([GEN-02]).
