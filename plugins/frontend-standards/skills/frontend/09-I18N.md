# 09 — Internationalisation

> Every user-visible string comes from a translation file, and every locale file holds
> **exactly the same keys, the same nesting and the same interpolation placeholders**.
> "Turkish has 5 keys fewer than English" is a CI failure, not a warning. This file also
> owns locale-aware formatting (`Intl`), the Turkish casing and collation traps, and how
> the language is chosen and switched. Read it when you add a string, a number, a date, a
> plural, or a second locale.

Out of scope: which URL carries the locale for indexed pages ([10](10-SEO-RENDERING.md) §4),
form field mechanics ([18](18-FORMS-VALIDATION.md)), sanitising HTML ([06](06-SECURITY.md) §1).

---

## 1. The parity rule and what counts as a string

**[I18N-01] MUST:** Every string a user can read goes through `t()` or `<Trans>`. This
includes button labels, headings, table column titles, empty states, tooltips, `title`,
`placeholder`, `aria-label`, `alt`, `document.title`, toast text, confirm dialogs, chart
axis labels, exported file names and column headers, and map layer names in the legend.
> **Why:** A literal is invisible until the second locale exists, and then it is invisible
> again because nothing fails. The reference deployment shipped a Turkish municipal portal
> with 40 English strings that had been "temporary" for eight months. Derived from [GEN-14].

**[I18N-02] MUST:** Every locale directory contains the same namespace files, and every
namespace file contains the same flattened key set, the same nesting, and the same
`{{placeholder}}` names per key as the default locale. `tools/check-i18n.mjs` enforces this
and its non-zero exit blocks the merge ([GEN-23]).
> **Why:** A key missing from `tr` renders the English text (or the raw key) to a Turkish
> user, silently, in production, for as long as nobody visits that screen. A placeholder
> mismatch (`{{count}}` in `en`, `{{adet}}` in `tr`) renders `{{adet}}` literally on screen.
> Neither throws. Parity is the only property that turns both into a build failure.
> Detail: §12.

**[I18N-03] MUST:** `eslint-plugin-i18next`'s `no-literal-string` runs at `error` severity
for JSX text nodes and for the attributes `title`, `placeholder`, `aria-label` and `alt`.
Exceptions are per-line `// eslint-disable-next-line` with a reason, never a rule downgrade.

```js
// eslint.config.js (excerpt)
import i18next from 'eslint-plugin-i18next'

export default defineConfig([
  {
    files: ['src/**/*.{ts,tsx}'],
    plugins: { i18next },
    rules: {
      'i18next/no-literal-string': ['error', {
        // JSX text plus the four attributes that reach a user or a screen reader.
        markupOnly: false,
        validateTemplate: true,
        onlyAttribute: ['title', 'placeholder', 'aria-label', 'alt'],
        // Technical attributes that are never displayed. Keep this list short and justified.
        ignoreAttribute: ['data-testid', 'className', 'id', 'type', 'role', 'href', 'to', 'src', 'key'],
        ignoreCallee: ['t', 'i18n.t', 'clsx', 'twMerge', 'console.warn', 'console.error'],
      }],
    },
  },
  {
    // Tests assert on visible text; that text is a literal by design.
    files: ['src/**/*.test.{ts,tsx}', 'src/test/**', 'e2e/**/*.ts'],
    rules: { 'i18next/no-literal-string': 'off' },
  },
])
```
> **Why:** Review does not catch literals reliably; a linter does, on every file, for free.
> The attribute list is not cosmetic: `aria-label` and `alt` are the only text a screen
> reader user gets ([GEN-16]). `check-standards.sh` also flags Turkish-specific letters in
> JSX, but only ESLint sees English literals ([TOOL-01]).

## 2. The key space: namespaces, files, naming

**[I18N-04] MUST:** Three namespaces are shared and owned by no feature: `common.*`
(actions and nouns reused everywhere: `common.save`, `common.cancel`, `common.loading`),
`errors.*` (user-facing failure text keyed by the normalised API error code:
`errors.NOT_FOUND`, `errors.NETWORK`, with `errors.unknown` as the fallback) and
`validation.*` (form messages: `validation.required`, `validation.tckn`). Nothing else is
global.
> **Why:** Without a home for "Save", every feature invents `parking.save`, `waste.save`
> and `report.save`, and the app ships three different Turkish words for one button.
> `errors.<code>` is the contract [OBS-09] and [API-13] depend on.

**[I18N-05] MUST:** Locale files live at `src/shared/i18n/locales/<lng>/<namespace>.json`,
one file per namespace, and every locale directory contains the identical file list.
`<lng>` is a lower-case BCP 47 tag (`tr`, `en`; a region variant such as `pt-br` only when
one is genuinely needed).

```
src/shared/i18n/locales/
├── tr/
│   ├── common.json
│   ├── errors.json
│   ├── validation.json
│   ├── parking.json
│   └── wasteTruck.json
└── en/
    ├── common.json          # the same five files, the same keys inside each
    ├── errors.json
    ├── validation.json
    ├── parking.json
    └── wasteTruck.json
```
> **Why:** One file per namespace keeps diffs readable and turns a missing namespace into a
> one-line CI error instead of 200 missing keys. A single `translation.json` per locale
> passes 2,000 keys quickly and then every translation PR conflicts with every other one.

**[I18N-06] MUST:** Keys are namespaced per feature. A feature's keys start with its
namespace in camelCase, matching the feature folder (`src/features/Parking` gives
`parking.list.title`), and shared UI text lives only under `common.*`, `errors.*` or
`validation.*`. A feature never reads another feature's keys.
> **Why:** Namespacing is what makes a feature deletable: removing `src/features/Parking`
> and `locales/*/parking.json` removes exactly its strings, and `check-i18n.mjs --src`
> reports nothing orphaned. It is also the precondition for lazy-loading a namespace later
> without touching a single call site.

**[I18N-07] MUST:** Key names follow `feature.section.element[.state]`, camelCase per
segment, at most four segments. Keys are identifiers, not sentences, and never contain the
translated text.

```jsonc
// GOOD - locales/tr/parking.json
{
  "list": {
    "title": "Otoparklar",
    "empty": "Kayıtlı otopark yok",
    "columns": { "name": "Ad", "capacity": "Kapasite" }
  },
  "detail": { "title": "Otopark detayı", "occupancy": "%{{percent}} dolu" },
  "actions": { "create": "Otopark ekle", "delete": "Sil" }
}
```
```jsonc
// BAD
{
  "Otoparklar": "Otoparklar",                        // the key is the Turkish text
  "parking_list_title_text_final_v2": "Otoparklar",  // not a hierarchy, snake case, versioned
  "Are you sure?": "Emin misiniz?"                   // an English sentence as a key
}
```
> **Why:** A key that is the English sentence changes whenever the English copy changes,
> which silently orphans every other locale. `check-i18n.mjs` reports `valueEqualsKey` as
> an error for exactly this shape.

## 3. Formatting: numbers, dates, currency

**[I18N-08] MUST:** Numbers, dates, times, percentages, currency, byte sizes, areas and
distances are formatted only by helpers in `src/shared/utils/format.ts`, and every helper
takes the active locale as an explicit argument. No `toLocaleString`, `Intl.*` or `toFixed`
in a component, a hook or a feature `lib/`.
> **Why:** `value.toFixed(2)` gives `1234.57` where a Turkish user expects `1.234,56`, and
> hard-coding `'tr-TR'` in 60 files makes the English build wrong in 60 places. One module
> also lets formatters be cached ([I18N-09]) and unit tested. Dates arrive as ISO strings
> ([API-18]) and are formatted at the edge, never stored as `Date` in query data.

```ts
// src/shared/utils/format.ts
const numberFormatters = new Map<string, Intl.NumberFormat>()

// Constructing an Intl formatter is expensive; a 5,000-row table would pay for it 15,000 times.
function numberFormatter(locale: string, options: Intl.NumberFormatOptions): Intl.NumberFormat {
  const key = `${locale}|${JSON.stringify(options)}`
  let formatter = numberFormatters.get(key)
  if (!formatter) {
    formatter = new Intl.NumberFormat(locale, options)
    numberFormatters.set(key, formatter)
  }
  return formatter
}

export const EMPTY_VALUE = '-'

export function formatNumber(
  value: number | null | undefined,
  locale: string,
  options: Intl.NumberFormatOptions = { maximumFractionDigits: 2 },
): string {
  if (value == null || !Number.isFinite(value)) return EMPTY_VALUE
  return numberFormatter(locale, options).format(value)
}

/** Turkish lira: symbol after the number, non-breaking space, no decimals for whole amounts. */
export function formatCurrency(value: number | null | undefined, locale: string, currency = 'TRY'): string {
  if (value == null || !Number.isFinite(value)) return EMPTY_VALUE
  return numberFormatter(locale, {
    style: 'currency',
    currency,
    currencyDisplay: 'narrowSymbol',
    minimumFractionDigits: Number.isInteger(value) ? 0 : 2,
  }).format(value)
}
```

**[I18N-09] MUST:** `Intl` formatter and collator instances are created once per
(locale, options) pair and cached in module scope, as above.
> **Why:** `new Intl.NumberFormat()` is among the most expensive standard-library
> constructors in the browser. One per cell in a virtualised table is a measurable INP
> regression ([PERF-23]); the cache removes it entirely and costs eight lines.

**[I18N-10] MUST:** Timestamps cross the API as ISO 8601 UTC and are rendered in
`Europe/Istanbul` by passing `timeZone` explicitly. A product that genuinely serves more
than one time zone takes the zone as a parameter and displays it next to the value; it
never relies on the browser's zone.

```ts
export function formatDateTime(
  iso: string | null | undefined,
  locale: string,
  timeZone = 'Europe/Istanbul',
): string {
  if (!iso) return EMPTY_VALUE
  const date = new Date(iso)
  if (Number.isNaN(date.getTime())) return EMPTY_VALUE
  return dateFormatter(locale, {
    day: '2-digit', month: '2-digit', year: 'numeric',
    hour: '2-digit', minute: '2-digit', hour12: false,
    timeZone,
  }).format(date)
}
```
> **Why:** Without `timeZone`, a support engineer in Berlin sees a work order stamped one
> hour before the operator in Istanbul created it, and the two disagree about what happened.
> `hour12: false` is stated explicitly because a browser whose UI language is `en-US` would
> otherwise render `14:05` as `2:05 PM` inside a Turkish product.

## 4. Error and validation text

**[I18N-11] MUST:** `src/shared/api/errorMessages.ts` maps every API error `code` in the
backend contract to an `errors.<code>` key, and every one of those keys exists in every
locale. An unmapped code falls back to `errors.unknown` plus the request id.

```ts
// src/shared/api/errorMessages.ts
import type { ApiError } from './errors'

// Exhaustive over the backend contract's code list. Adding a code here without adding
// errors.<code> to every locale fails check-i18n.mjs with usedKeyMissing.
const CODE_TO_KEY = {
  VALIDATION: 'errors.VALIDATION',
  NOT_FOUND: 'errors.NOT_FOUND',
  FORBIDDEN: 'errors.FORBIDDEN',
  CONFLICT: 'errors.CONFLICT',
  RATE_LIMITED: 'errors.RATE_LIMITED',
  NETWORK: 'errors.NETWORK',
  TIMEOUT: 'errors.TIMEOUT',
  UNKNOWN: 'errors.unknown',
} as const satisfies Record<string, string>

export function errorMessageKey(error: ApiError): string {
  return CODE_TO_KEY[error.code as keyof typeof CODE_TO_KEY] ?? 'errors.unknown'
}
```
> **Why:** The backend `message` field is English and developer-facing ([API-13]); mapping
> by `code` is the only stable path to a translated sentence. A `Record` keyed by the code
> makes a newly introduced backend code appear as a missing key in CI rather than as
> English text in a Turkish toast.

**[I18N-12] MUST:** zod schemas and react-hook-form carry i18n **keys**, not translated
sentences. Translation happens at render time, so switching language re-renders the message.

```ts
// GOOD - the key travels, the translation happens in the component
const ParkingFormSchema = z.object({
  name: z.string().min(1, { message: 'validation.required' }),
  capacity: z.number().int().positive({ message: 'validation.positiveInteger' }),
})
// in the component:
// {errors.name && <p role="alert">{t(errors.name.message ?? 'validation.invalid')}</p>}
```
```ts
// BAD - the sentence is frozen at module evaluation, before the user picks a language
const Bad = z.object({ name: z.string().min(1, { message: i18n.t('validation.required') }) })
```
> **Why:** Schemas are module-level constants, evaluated once at import time and never
> again after a language switch. Wiring: [18](18-FORMS-VALIDATION.md) §3.

## 5. Runtime setup: `src/shared/i18n/config.ts`

**[I18N-13] MUST:** i18next is initialised exactly once, in `src/shared/i18n/config.ts`,
imported for its side effect from `src/main.tsx` before the first render, with the options
below. No feature calls `i18n.init`, `addResourceBundle` or `changeLanguage` directly; the
only permitted entry point is the helper in [I18N-29].

```ts
// src/shared/i18n/config.ts
import i18n from 'i18next'
import LanguageDetector from 'i18next-browser-languagedetector'
import { initReactI18next } from 'react-i18next'

import common_en from './locales/en/common.json'
import errors_en from './locales/en/errors.json'
import parking_en from './locales/en/parking.json'
import validation_en from './locales/en/validation.json'
import common_tr from './locales/tr/common.json'
import errors_tr from './locales/tr/errors.json'
import parking_tr from './locales/tr/parking.json'
import validation_tr from './locales/tr/validation.json'

export const SUPPORTED_LOCALES = ['tr', 'en'] as const
export type Locale = (typeof SUPPORTED_LOCALES)[number]
export const DEFAULT_LOCALE: Locale = 'tr'

// One i18next namespace ('translation') holding every feature namespace as a key prefix.
// Rationale: a component can use errors.* without an ns argument, and check-i18n.mjs
// compares one flat key space. Split into real i18next namespaces only when lazy loading
// arrives (Open questions).
const resources = {
  tr: { translation: { common: common_tr, errors: errors_tr, validation: validation_tr, parking: parking_tr } },
  en: { translation: { common: common_en, errors: errors_en, validation: validation_en, parking: parking_en } },
} as const

void i18n
  .use(LanguageDetector)
  .use(initReactI18next)
  .init({
    resources,
    supportedLngs: SUPPORTED_LOCALES,
    fallbackLng: DEFAULT_LOCALE,
    nonExplicitSupportedLngs: true,   // a browser reporting 'tr-TR' resolves to 'tr'
    returnNull: false,                // a null value would type t() as string | null everywhere
    returnEmptyString: false,         // an empty value falls back instead of rendering nothing
    debug: false,                     // never true in a committed file: one console line per lookup
    saveMissing: import.meta.env.DEV,
    missingKeyHandler: import.meta.env.DEV
      ? (lngs, _ns, key) => { throw new Error(`[i18n] missing key "${key}" for ${lngs.join(',')}`) }
      : undefined,
    detection: {
      order: ['localStorage', 'navigator'],
      lookupLocalStorage: 'appLocale',
      caches: ['localStorage'],
    },
    interpolation: { escapeValue: false }, // React escapes; double escaping renders &amp;
  })

export default i18n
```
> **Why:** `escapeValue: false` is correct only because React escapes its children, which is
> exactly why [I18N-20] forbids feeding a translation to `dangerouslySetInnerHTML`.
> `debug: true` left in a commit writes a console line per lookup and costs measurable frame
> time on a table render. SEO-indexed products replace the `detection` block per [SEO-08].

**[I18N-14] MUST:** `fallbackLng` is a runtime safety net for a key that slipped through,
never a translation strategy. A key that resolves through the fallback is a defect; CI
catches it as `missingKey` before it can reach a browser.
> **Why:** With a silent fallback a Turkish product degrades to English one key at a time
> and nobody notices until a citizen complains. The fallback exists so a single missing key
> does not render `parking.list.title` on screen, not so translation can be deferred.

**[I18N-15] MUST:** With three locales or fewer, all resources are imported statically and
bundled, as above. Beyond three locales, only the default locale is bundled and the rest are
loaded lazily over HTTP, which requires an approved backend package ([GEN-03], see Open
questions).
> **Why:** A full locale bundle is roughly 15 to 40 KB gzipped per language. Two or three
> fit inside the initial-JS budget ([PERF-02]); eight do not, and no single visitor uses
> more than one of them.

**[I18N-16] MUST:** In development and in tests a missing key throws, with the key name in
the message. In production the handler is absent and the fallback applies.
> **Why:** Throwing in development converts "I forgot the `tr` key" from a production report
> into a red screen on the developer's own machine, before the commit exists.

## 6. Typed keys

**[I18N-17] MUST:** `t()` is typed against the real key set. `src/shared/i18n/keys.d.ts` is
generated from the default locale's files, committed with the `// GENERATED` header
([STR-29]), regenerated by `npm run gen:i18n-keys`, and CI fails on a diff ([CI-12]).

```ts
// src/shared/i18n/keys.d.ts
// GENERATED - do not edit; run npm run gen:i18n-keys
import type common from './locales/tr/common.json'
import type errors from './locales/tr/errors.json'
import type parking from './locales/tr/parking.json'
import type validation from './locales/tr/validation.json'

declare module 'i18next' {
  interface CustomTypeOptions {
    defaultNS: 'translation'
    returnNull: false
    resources: {
      translation: {
        common: typeof common
        errors: typeof errors
        validation: typeof validation
        parking: typeof parking
      }
    }
  }
}
```
> **Why:** `t('parking.list.titel')` is a runtime shrug (it renders the key) and a
> compile-time error once `CustomTypeOptions` is declared. This is the cheapest of the three
> parity mechanisms because it fires in the editor, before the commit.

**[I18N-18] MUST NOT:** Build a key by concatenation or template literal from a runtime
value. A key derived from data goes through an exhaustive `as const` map, so a new enum
member becomes a TypeScript error.

```tsx
// BAD - no tool can see this key; check-i18n reports the whole subtree as unused
<span>{t(`parking.status.${status}`)}</span>

// GOOD - exhaustive, typed, greppable
const STATUS_KEY = {
  open: 'parking.status.open',
  full: 'parking.status.full',
  closed: 'parking.status.closed',
} as const satisfies Record<ParkingStatus, string>

<span>{t(STATUS_KEY[status])}</span>
```
> **Why:** Dynamic keys defeat the type check, the unused-key report and grep at once. When
> the backend adds `maintenance`, the map version fails `tsc`; the template-literal version
> renders `parking.status.maintenance` to a citizen.

## 7. Interpolation and rich text

**[I18N-19] MUST:** Variable parts are interpolated with named placeholders (`{{count}}`,
`{{name}}`, `{{date}}`). Sentences are never assembled from concatenated translated
fragments, and the placeholder names are identical in every locale.

```tsx
// GOOD
t('parking.detail.occupancy', { name: parking.name, percent: formatNumber(pct, locale) })
// tr: "{{name}} otoparkı %{{percent}} dolu"
// en: "{{name}} car park is {{percent}}% full"

// BAD - word order is not a constant across languages
<span>{t('parking.detail.the')} {parking.name} {t('parking.detail.isFull')}</span>
```
> **Why:** Turkish places the possessive suffix and the percent sign where English does not.
> A sentence split across three keys cannot be reordered by a translator, so at least one
> language always reads wrong. It also breaks the placeholder parity check, which can only
> compare whole values.

**[I18N-20] MUST:** Rich text (a link or a bold span inside a sentence) uses `<Trans>` with
component slots. A translation value is never passed to `dangerouslySetInnerHTML`, not even
through the `SafeHtml` wrapper.

```tsx
import { Trans, useTranslation } from 'react-i18next'
import { Link } from 'react-router-dom'

export function PrivacyNotice() {
  const { t } = useTranslation()
  return (
    <p>
      {/* tr: "Devam ederek <0>gizlilik politikasını</0> kabul etmiş olursunuz." */}
      <Trans i18nKey="common.privacyNotice" t={t} components={[<Link key="0" to="/gizlilik" />]} />
    </p>
  )
}
```
> **Why:** With `escapeValue: false`, a translation reaching `innerHTML` becomes a stored
> XSS sink the moment translations are editable by anyone but a developer ([SEC-01],
> [SEC-04]). `<Trans>` renders React elements, so the markup can never be attacker data.

**[I18N-21] MUST:** Locale values contain no HTML except the numbered or named tags a
`<Trans>` call supplies components for. No `<br>`, no `&nbsp;`, no inline styles in JSON.
> **Why:** Layout inside a translation file is layout no stylesheet can override, and it is
> duplicated (differently, and wrongly) in every locale. Use `whitespace-pre-line` or a
> second key.

## 8. Plurals and context

**[I18N-22] MUST:** Countable text uses i18next's CLDR plural suffixes with a `count`
option. Turkish and English both use the `one`/`other` set, so every plural base key has
exactly `_one` and `_other` in **every** locale; a locale with a different form set is a CI
error (`pluralMismatch`).

```jsonc
// locales/en/parking.json                     // locales/tr/parking.json
{ "list": {                                    // { "list": {
    "count_one": "{{count}} car park",         //     "count_one": "{{count}} otopark",
    "count_other": "{{count}} car parks" } }   //     "count_other": "{{count}} otopark" } }
```
```tsx
<h2>{t('parking.list.count', { count: items.length })}</h2>
```
> **Why:** Turkish does not inflect a noun after a numeral, so `_one` and `_other` hold the
> same text; that is correct, and the checker exempts plural siblings from the
> duplicate-value warning. What is not correct is deleting `_one` from `tr` because it looks
> redundant: i18next then resolves `count: 1` to nothing at all.

**[I18N-23] MUST:** Context variants use i18next's `_<context>` suffix over a closed union
of contexts, and every variant exists in every locale. A context value that comes from the
API is validated against that union before it reaches `t()`.

```jsonc
{ "assignment": { "title_driver": "Sürücü ataması", "title_vehicle": "Araç ataması" } }
```
```tsx
t('wasteTruck.assignment.title', { context: kind }) // kind: 'driver' | 'vehicle'
```
> **Why:** An unknown context silently falls back to the base key, and if the base key does
> not exist (the common shortcut, because it is never displayed) the raw key is rendered.

## 9. Turkish specifics

Turkish has two letters, dotted `İ`/`i` and dotless `I`/`ı`, that make locale-independent
string operations wrong rather than merely ugly. These rules apply to any product that
ships `tr`.

**[I18N-24] MUST NOT:** Call `toLowerCase()` or `toUpperCase()` on text that may be Turkish.
Use `toLocaleLowerCase('tr-TR')` and `toLocaleUpperCase('tr-TR')` through a helper.

```ts
// The locale-independent mapping is wrong in both directions for Turkish:
'I'.toLowerCase()               // 'i'   WRONG in Turkish; the correct result is 'ı' (dotless)
'I'.toLocaleLowerCase('tr-TR')  // 'ı'   correct
'i'.toUpperCase()               // 'I'   WRONG in Turkish; the correct result is 'İ' (dotted)
'i'.toLocaleUpperCase('tr-TR')  // 'İ'   correct
'İSTANBUL'.toLowerCase()        // 'i' + a combining dot, which no longer equals 'istanbul'

// src/shared/utils/text.ts
export function foldForSearch(value: string, locale: string): string {
  // Case-insensitive, accent-insensitive comparison key for filter boxes.
  return value.toLocaleLowerCase(locale).normalize('NFD').replace(/\p{Diacritic}/gu, '')
}
```
> **Why:** A "contains" filter written with `toLowerCase()` cannot find `İstanbul` when the
> user types `istanbul`, because the invariant lowercase of `İ` is `i` followed by a
> combining dot. This is the most common Turkish defect in a search box and it reaches the
> user as "the search is broken".

**[I18N-25] MUST:** User-visible lists are sorted with a cached `Intl.Collator(locale)`,
never with `a < b`, `sort()` without a comparator, or `localeCompare()` without a locale.

```ts
// Turkish alphabet: ... g, ğ, h, ı, i, j ... o, ö, p ... s, ş, t, u, ü, v ...
const collator = new Intl.Collator('tr', { numeric: true, sensitivity: 'base' })
const sorted = [...neighbourhoods].sort((a, b) => collator.compare(a.name, b.name))
```
> **Why:** Code-point ordering puts every Turkish-specific letter after `z`, so `Çekmeköy`
> sorts after `Zeytinburnu` and users conclude the list is unsorted. `numeric: true`
> additionally sorts `Blok 2` before `Blok 10`.

**[I18N-26] MUST:** Turkish presentation defaults, produced through `format.ts` and never by
hand: decimal comma and thousands dot (`1.234,56`), date `dd.MM.yyyy`, 24-hour time
(`14:05`), the currency symbol after the number with a non-breaking space (`1.234,56 ₺`),
and the percent sign before the number in Turkish (`%42`) versus after it in English
(`42%`).
> **Why:** `Intl.NumberFormat('tr-TR')` produces all of these correctly, which is precisely
> why hand-formatting is forbidden. The percent position inside a sentence is the one case
> `Intl` will not fix for you, so it lives in the translation string ([I18N-19]), not in
> code.

**[I18N-27] MUST:** A numeric input parses the displayed format before `Number()`: remove
the group separator, convert the decimal separator to a point, and reject anything left.

```ts
// src/shared/utils/parseNumber.ts
export function parseLocaleNumber(input: string, locale: string): number | null {
  const parts = new Intl.NumberFormat(locale).formatToParts(12345.6)
  const group = parts.find((p) => p.type === 'group')?.value ?? ''
  const decimal = parts.find((p) => p.type === 'decimal')?.value ?? '.'
  const normalised = input.trim().split(group).join('').replace(decimal, '.')
  if (normalised === '' || !/^-?\d+(\.\d+)?$/.test(normalised)) return null
  const value = Number(normalised)
  return Number.isFinite(value) ? value : null
}
```
> **Why:** `Number('1.234,56')` is `NaN` and `Number('1.234')` is `1.234`, so a Turkish user
> typing one thousand two hundred thirty four stores `1.234` as a car park's capacity, with
> no error anywhere. Form wiring: [18](18-FORMS-VALIDATION.md) §5.

## 10. Choosing and switching the language

**[I18N-28] MUST:** App-type products (authenticated, `noindex`, Tier 0 in
[10](10-SEO-RENDERING.md) §1) persist the chosen locale in `localStorage` under `appLocale`
and detect from `navigator` on first visit. SEO-indexed products carry the locale in the URL
prefix (`/tr/...`, `/en/...`) and disable localStorage detection ([SEO-08]). A product uses
one mechanism, never both.
> **Why:** A localStorage-detected locale means one URL serves two languages, so Googlebot
> indexes whichever the crawler happened to receive and the `hreflang` graph is a lie.
> Detail: [10](10-SEO-RENDERING.md) §4.

**[I18N-29] MUST:** Changing the language updates `document.documentElement.lang` and `dir`
in the same operation, and is the only code path that calls `i18n.changeLanguage`.

```ts
// src/shared/i18n/changeLocale.ts
import i18n, { type Locale } from './config'

const RTL_LOCALES = new Set(['ar', 'fa', 'he'])

export async function changeLocale(locale: Locale): Promise<void> {
  await i18n.changeLanguage(locale)
  const root = document.documentElement
  root.lang = locale
  root.dir = RTL_LOCALES.has(locale) ? 'rtl' : 'ltr'
}
```
> **Why:** `<html lang>` drives screen-reader pronunciation, the browser's translation
> prompt, hyphenation and `:lang()` selectors. Vite copies `index.html` verbatim, so a
> hard-coded `<html lang="en">` on a Turkish app stays wrong forever unless it is set at
> runtime.

**[I18N-30] MUST:** The active locale is read from `i18n.language` via
`const { i18n } = useTranslation()` and passed into the format helpers, so a language change
re-renders formatted values. A module-level `const locale = i18n.language` is forbidden.
> **Why:** A captured locale leaves numbers and dates Turkish after the user switches to
> English, which is the classic half-translated screen and is invisible in review because
> the first render is correct.

## 11. i18n at the edges: map, exports, documents

**[I18N-31] MUST:** Map label layers resolve the name field with `coalesce` and fall back to
the neutral field, and the expression is updated on language change with
`setLayoutProperty`, never by removing and re-adding the layer.

```ts
// src/features/Parking/components/ParkingLayer.tsx (excerpt)
const labelExpression = (lng: string) => ['coalesce', ['get', `name_${lng}`], ['get', 'name']]

map.setLayoutProperty('parking-points-label', 'text-field', labelExpression(i18n.language))
```
> **Why:** Tile data carries `name_tr` for some features and only `name` for the rest, so
> `['get','name_tr']` alone renders empty labels for the remainder. Re-adding a layer to
> change a label reorders the style and drops `feature-state`, which loses hover and
> selection ([MAP-13], [08](08-MAP-MAPLIBRE.md)).

**[I18N-32] MUST:** PDF and Excel exports use the active locale for column headers, number
and date formats and the file name, and the PDF font embedded from `public/fonts/` covers
the Turkish glyph set (ç ğ ı İ ö ş ü).
> **Why:** jsPDF's built-in Helvetica has no `ğ` or `ş`, and drops them without an error, so
> `Çağdaş` prints as `Cadas` in an official municipal document. Self-hosted fonts are
> already required by [PERF-19] and [SEC-14].

**[I18N-33] SHOULD:** Components are written RTL-ready: CSS logical properties (Tailwind
`ms-*`/`me-*`, `ps-*`/`pe-*`, `text-start`/`text-end`) instead of physical left and right,
and no layout that depends on `float: left`.
> **Why:** No current product ships an RTL locale, which is why this is SHOULD. Writing it
> logically costs nothing today and is the difference between a two-week and a two-month
> Arabic locale later. Directional icons and map controls are known exceptions and are
> handled when a real RTL locale is added.

## 12. The parity gate: `tools/check-i18n.mjs`

**[I18N-34] MUST:** CI runs the checker on every PR and its non-zero exit blocks the merge.

```bash
node frontend-standards/tools/check-i18n.mjs src/shared/i18n/locales --src src --default tr
```

The script's contract, as implemented:

| Aspect | Behaviour |
|---|---|
| Input | `<localesDir>/<lng>/<namespace>.json`. Each subdirectory is a locale, each `.json` file a namespace |
| Key prefixing | `parking.json` contributes `parking.*`. The legacy name `translation.json` contributes unprefixed keys, and a `{ "translation": { ... } }` wrapper inside it is unwrapped |
| Options | `--src <dir>` enables the source scan, `--default <lng>` sets the source-of-truth locale (default `tr`), `--json` prints the full machine-readable report |
| Exit codes | `0` clean, `1` at least one error, `2` invalid arguments |
| Dependencies | None. Node 24, ESM, no install step |

Errors (exit 1):

| Finding | Meaning |
|---|---|
| `missingKey` / `extraKey` | The locale has fewer or more keys than the default locale |
| `missingFile` / `extraFile` | The locale's namespace file list differs from the default locale's |
| `placeholderMismatch` | The `{{...}}` names differ between the default locale and this locale for one key |
| `pluralMismatch` | The plural form set differs between locales for one base key (reported once per base, not once per form) |
| `pluralMissingOther` | A plural group has no `_other` form, which every language needs |
| `duplicateKey` | One flattened key is defined by two namespace files in the same locale |
| `emptyValue` | A value is empty or whitespace only |
| `valueEqualsKey` | The value is literally the key, the usual sign of a copy-paste placeholder |
| `nestedKeyMissing` | A `$t(other.key)` reference points at a key that does not exist |
| `nonStringValue` | A leaf is a number, boolean, null or array. Values must be strings |
| `invalidJson` | Parse failure, reported with line and column |
| `usedKeyMissing` | A key used in `src/` (`t('x')` or `i18nKey="x"`) is absent from the default locale |
| `missingDir` | The locales directory or the default locale's directory does not exist |

Warnings (they do not affect the exit code): `unusedKey` (a default-locale key that no
`t()` call, `i18nKey` attribute or dynamic prefix covers), `duplicateValue` (two unrelated
keys with identical text, a merge candidate), `singleLocale` (only one locale exists, so
there is nothing to compare).

**[I18N-35] MUST:** Findings are fixed, not worked around. There is no ignore file. A key
reported as `unusedKey` is either deleted or its call site is converted to an exhaustive map
([I18N-18]) so the scanner can see it.
> **Why:** The scanner recognises `t('literal')`, `i18nKey="literal"` and a template-literal
> prefix (`` t(`parking.status.${x}`) `` covers `parking.status.*`). Everything it cannot see
> is a pattern the standard already forbids, so an ignore list would only hide violations.

**[I18N-36] MUST:** `--default` is the product's source locale (`tr` for the municipal
products). It decides which side of a mismatch is reported as `missingKey` rather than
`extraKey`, so it is set once per repo, identically in the CI step and in `package.json`'s
`check:i18n` script.

**[I18N-37] MUST:** Non-string leaves are not used in locale files. A list rendered from
translations is a set of numbered keys plus an exhaustive map ([I18N-18]), not a JSON array
with `returnObjects: true`.
> **Why:** The checker reports arrays and numbers as `nonStringValue` errors, deliberately:
> an array has no key-level parity, so `tr` can have three bullet points where `en` has five
> and nothing detects it.

## 13. Testing

**[I18N-38] MUST:** Component tests render with the real default-locale bundle (not a
`t: (key) => key` stub) and assert on the visible translated text.

```tsx
// src/test/renderWithProviders.tsx (excerpt)
import { I18nextProvider } from 'react-i18next'
import i18n from '@/shared/i18n/config'   // the real instance with the real tr resources

export function renderWithProviders(ui: ReactElement) {
  return render(<I18nextProvider i18n={i18n}>{ui}</I18nextProvider>)
}
```
```tsx
// A missing tr key makes this fail, which is the point.
it('shows the empty state', () => {
  renderWithProviders(<ParkingList items={[]} />)
  expect(screen.getByText('Kayıtlı otopark yok')).toBeInTheDocument()
})
```
> **Why:** A `t: (key) => key` mock makes every test pass with no translations at all, so
> the suite certifies a screen that renders `parking.list.empty` to a user. Asserting on the
> real Turkish text also documents the copy in a place reviewers read.
> Detail: [13](13-TESTING.md) §4.

**[I18N-39] MUST:** The Vitest setup installs the throwing `missingKeyHandler` from
[I18N-16], so any key a test touches that is absent from the default locale fails that test
with the key name in the message.

## 14. Translation workflow

**[I18N-40] MUST:** The default locale is the source of truth, and a commit that adds a key
adds it to **every** locale file in the same commit. A locale without a translation yet gets
the reviewed default-locale text plus a `TODO(i18n)` note in the PR description, never an
empty string and never a missing key.
> **Why:** "We will add the English later" produces exactly the drift [I18N-02] exists to
> prevent, and an empty value renders a blank button rather than an obviously untranslated
> one. `emptyValue` is an error in the checker for this reason.

**[I18N-41] MUST:** Deleting or renaming a feature deletes or renames its namespace files in
every locale in the same PR. The checker's `unusedKey` warnings are the review evidence that
nothing was left behind.

**[I18N-42] MUST:** A translation change is an ordinary PR reviewed by someone who reads the
language. Locale JSON is not edited on the server, inside the container, or through an admin
screen.
> **Why:** Resources are bundled at build time ([I18N-15]), so a value edited anywhere else
> is either overwritten by the next deploy or, worse, a translation-shaped injection point
> ([I18N-20]).
